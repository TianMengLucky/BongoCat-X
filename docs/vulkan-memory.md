# Vulkan 内存与异步生命周期

本次改造在 dev 上保留稳定插件 ABI 和 Rust 不可信数据解析。源代码没有
发现逐帧无界增长的回读队列；原实现是单份全帧缓冲。因此不将内存读数
超过 100 MB 直接归因于回读泄漏，也不承诺整机占用降至 30–50 MB。

## 固定槽与同步边界

- 主机有两个独立帧槽，各持有一个命令池、初始化/帧末命令和完成 Fence。
  推进只使用 0/1 环形下标。复用槽位前等待它的 Fence，再重置命令池并
  释放命令池内部空闲存储，不随运行时间新增命令池或同步对象。
- 帧末回读与图像转换提交异步返回。CPU 读取 RGBA/BGRA 时才等待写入帧
  的 Fence。普通交换链使用至多两份回读映射；Windows 分层窗口逐帧
  消费当前像素，复用一份映射，写入前等待前一个写入者。
- 回读有效负载为 W × H × 4 × 槽数，另有驱动对齐开销。
  同尺寸直接复用；尺寸变化清理旧大小映射；同尺寸交换链重建保留池。
- Present 信号量按交换链图像分配。帧 Fence 只证明命令执行完成，不能
  证明呈现已消费信号量；再次获取相同图像才允许再次使用该信号量。
  依据：[Vulkan 官方说明](https://docs.vulkan.org/guide/latest/swapchain_semaphore_reuse.html)。
- 队列 Fence 检查点替代正常路径中的 vkQueueWaitIdle。共享背景修改、
  失败恢复必须先同步；交换链重建和最终销毁保留设备 idle 等待。
- 已提交标记仅在 vkQueueSubmit 成功后设置。提交失败后不等待尚未提交
  的 Fence；等待失败后停止资源复用，不提前销毁未知完成状态的 staging。

## 插件资源

Live2D 使用两个上传批次槽，保留批次命令和 staging 到各自 Fence 完成；
继续限制每批 32 条命令/约 16 MiB，单张大纹理可以超过该字节阈值。
完成的 staging 在下一次绘制检查时也会回收，无需等待交换链重建。
绘制提交返回时不等待完成；下次修改几何、遮罩、描述符或 SDK 命令缓冲
前等待绘制 Fence。多 pass 复用同一套资源时仍需在复用点等待。

Inox2D 使用两个独立提交池和 Fence。纹理 staging 留在对应槽；绘制的
描述符池、uniform/vertex buffer、framebuffer 保留至下次修改前的 Fence
等待结束。错误路径放弃未提交的命令，不再自动提交半成品。
默认分配块从设备 16 MiB/主机 8 MiB 改为分配器支持的最小 4 MiB/4 MiB；
显式大分配仍是 64 MiB/16 MiB。块大小是分配粒度，不是总内存上限。

为压缩重资源，模型保留一套共享几何/中间目标/次级录制资源，下一次
改写前等待。这允许提交后 CPU 继续处理逻辑，但不声称同一模型的两帧
可以同时访问共享可写资源。主机两帧槽与模型资源集合是不同的生命周期。
旧插件宿主的同步 one-shot 服务语义保持不变；内置插件用自身异步槽，
避免旧插件仍在提交返回后释放 staging 时产生兼容性事故。

取消加载、替换正在使用的图像、重建共享目标及销毁插件是同步边界。
CPU 解码像素复制到 staging 后可以释放；GPU staging 必须等待 Fence。
不按“过一帧就安全”推断完成，也不依赖复杂退役队列或递增帧号。

## 其他内存优化

音频声部共享同路径不可变 PCM，各自保留独立游标，最后一个声部卸载后
才释放 PCM。Windows 不再由轮询主动打开音频设备，空闲 5 秒卸载引擎。
长音频仍全量解码；不同文件各有 PCM，声音首次恢复可能有设备启动延迟。
贡献者数据按关于页请求，离页取消任务并释放资源；封面纹理离模型页释放。
模型质量、平台支持及用户配置的显式大分配选项保持原行为。

## 测试方式

自动化用例 vulkan-fixed-slots 使用模拟分发，对 100 次槽循环验证数量
有界、提交时无 CPU 等待、按图像选择呈现信号量、失败后不等待空 Fence，
以及 staging 在等待成功之前不会销毁。audio 使用离线设备验证同一 PCM
共享、原声部销毁后其他声部继续有效和空闲整体释放。
vulkan-async-submission 直接链接 Live2D 提交实现，用模拟 Vulkan 验证
异步绘制、两槽上传、32 命令批次、取消、提交失败和等待失败后的生命周期。
模拟测试覆盖所有权与错误处理，不代替真实驱动验证。

手动测试建议：

1. 选择 Vulkan，切换大纹理模型、缩放窗口、连续切换纹理质量；检查画面、
   遮罩、点击命中、截图及封面没有闪烁或错帧。
2. 设置窗口及各页开关 20 次；同音效叠加触发后等待超过 5 秒再播放。
3. 关闭/移除背景、模型加载中取消或失败、插件切换及正常退出。
4. 同一模型、尺寸、质量和 Release 构建下比较工作集、私有提交、GPU
   内存、加载峰值及帧时间；用多轮稳定值判断回落和持续增长。
5. Windows 分层窗口当前帧 CPU 消费仍会等待 GPU；不要把异步提交接口
   等同于所有场景零等待。Linux 真机及其他驱动需要单独验证。

不通过强制裁剪活跃工作集制造较低读数；最终内存还受模型尺寸、纹理、
字体和驱动缓存影响。测试包不包含 Cubism SDK 或 Core，Core 由用户提供。

## 自动内存管理（2026-10-14）

删除设置中的低内存模式及其配置、插件和渲染限制。旧 application.lowMemoryMode
字段读取时忽略，保存时不再写出；C/Rust 结构保留一个零值字节以维持既有字段偏移。
插件 v1 的第 4 位保留但不再请求或报告。画质、动态纹理、大型渲染优化和
显存／系统内存优先级继续由各自设置控制，设置窗口恢复独立 OpenGL 上下文。

参考 [bongocat-turbo](https://github.com/Fid-falling/bongocat-turbo/tree/05b74ca0d158069f387c0729e7bfa4246e855c3f)
的按需分配和闲置资源回收原则，适配现有主机／动态插件架构：

- Live2D Vulkan 的 VMA 大堆首选块大小默认 1 MiB；只有明确启用大型分配
  才采用 16 MiB。由 VMA 处理对齐、子分配、增长和超大资源独立分配；
  首选块大小不是总内存或驱动实际分配的硬上限。上传 staging 仍独立分配并
  保留至 Fence 完成，避免扩大长期资源池。
- Windows 分层窗口默认使用一个拥有的 Vulkan 颜色目标，取消不会用于
  实际呈现的 WSI 交换链。两帧命令槽仍保留；共享目标复用前等待上一写入者，
  分层回读复用一份映射。Linux 保留正常 WSI 呈现与按图像管理的信号量。
- 隐藏或最小化后回收回读缓冲。先等待帧 Fence，再用队列检查点确保包括
  前景上传在内的所有引用已完成；等待或提交失败时不释放未知完成状态资源。
  已完成的分层待呈现帧可以丢弃；WSI 待呈现帧保留正常信号量消费流程。
  无缓存时不重复提交检查点。恢复绘制按当前尺寸重新分配。
- 原生背景上传完成并确认后端持有对应版本后，释放 CPU 临时合成表面。
  GPU 背景继续缓存，只有尺寸、素材或后端失效时重建。

参考仓库使用不同的 Vulkan／Cubism 桥，本次没有复制其 SDK 源码、工作集驱逐
或遮罩降采样策略，也没有降低用户选择的模型画质。保留现有完整 GPU 同步边界。

新增闲置回收模拟用例覆盖帧等待失败、检查点提交失败、回收后重复轮询、
分层待呈现帧丢弃，以及 WSI 待呈现帧保留。配置测试覆盖旧字段忽略及停止保存。
本次未构建、未运行这些编译型测试、未启动应用或测量真实驱动内存；
前文的历史测试结果不代表本次修改已通过实机验证。

## Live2D 与设置界面资源复查

- Live2D OpenGL 离屏池在表情所需目标数下降并稳定 0.5 秒后释放闲置目标，
  仍由 SDK 的使用标记保护当前目标；刚载入模型在首帧处理旧池。短暂表情
  切换保留复用余量，避免逐帧释放／重建。遮罩尺寸、MSAA 和纹理画质不变。
- Vulkan 几何使用已有交错打包缓冲比较位置和 UV，包括系统内存选项及原始
  SDK 分配回退，不再为每个网格保留另外两份 CPU 数组。绘制 Fence 完成后
  才读取或改写映射；仍只提交有变化的网格范围。
- 纹理上传及渲染器初始化的索引上传都在加载返回前等待上传 Fence，避免
  尚未显示的模型保留末批暂存。隐藏窗口的主机回收也覆盖只有上传、没有
  回读的情况，队列检查点完成后才销毁暂存和上传池；失败时保留资源。
- 释放模型渲染资源时同时释放 Alpha、纹理记录和边界缓存的容器容量。
  回滚仍可从模型文件重建。Vulkan 画质调整在所有纹理实际尺寸相同时直接
  更新画质记录，不重新解码；有后台刷新或尺寸变化时仍走原有重载流程。
- 设置界面 CPU 顶点／索引缓冲以 64／32 KiB 起步，保留原来的最大限制，
  按需增长。完整帧呈现并停止交互动画后，按上一帧需求和二次幂余量收缩
  CPU／OpenGL GPU 容量。软件分片尚未完成、构建帧时禁止回收。
- Nuklear 转换命令和原始绘图命令按实际缓冲容量回收；修正原先用清帧后
  为零的 `allocated` 判断容量而不会触发回收的问题。只处理动态、已经
  清空且没有持久后向分配的缓冲，窗口状态继续保留在独立 pool。诊断日志
  同时记录 CPU 和 GPU 绘制容量。依据仓库固定版本的
  [Nuklear 源码](https://github.com/Immediate-Mode-UI/Nuklear/blob/8109cfbabe04f8705408c5d8ab1a6cd48649ccda/nuklear.h#L8284)。
- 设置窗口缓存画面只更新复用缓冲的四个顶点和六个索引，不逐次替换整个
  VBO／EBO 分配；容量记录和实际分配保持一致。
- 关于页保留可见头像及 24 个逻辑像素的悬停余量，每帧至多上传四张，
  滚出视区后释放 native 纹理。解码像素保留以支持资源／DPI 重建；上传
  失败不会自发触发无限重绘。离开页面仍取消请求并释放整份数据。
- Windows 软件设置界面的封面、标志和预览图复用现有 WIC 有界解码，
  避免在应用层先持有完整 RGBA 再缩小。不支持的格式保留通用解码回退；
  编解码器自身是否分配全图由实现决定。效果缓存预算在临时栅格分配前
  检查，GL 区分 R8 遮罩与 RGBA，软件纹理按 RGBA 计费。

以上是资源所有权与容量的源码审查结论，不是工作集或显存的实测结果。
驱动分配、模型原始纹理、全量解码回退、字体 glyph 数据仍可能占据主要
内存。需要分别记录加载峰值、稳定绘制、设置页切换、DPI 重建及隐藏后的
读数，才能量化收益。相关回归用例为 `ui-software-memory` 和
`vulkan-fixed-slots`；按仓库约定，只有明确要求构建时才编译和执行。
